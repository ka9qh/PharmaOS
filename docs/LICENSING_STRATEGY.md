# استراتيجية الترخيص التجاري - PharmaOS (لأنه منتج يُباع لعدة صيدليات)

## الفكرة
كل صيدلية = نسخة مستقلة + ترخيص مرتبط بمعرف جهازها الفريد (Hardware ID).

## قرار أمان مهم: الترخيص منفصل تمامًا عن تشفير قاعدة البيانات
**لا يعتمد مفتاح تشفير قاعدة البيانات على معرف الجهاز إطلاقًا** (راجع
core/security/database_encryption.dart - لم يتغير منذ Phase 1). السبب: لو
تذبذب معرف الجهاز ولو بشكل بسيط (تحديث ويندوز، تغيير قطعة عتاد)، وكان مفتاح
التشفير مرتبطًا به، ستفقد الصيدلية كل بياناتها نهائيًا وبلا أي إمكانية استرجاع
(SQLCipher لا يملك "استرجاع كلمة مرور منسية"). المخاطرة أكبر بكثير من الفائدة
الأمنية الهامشية. لذلك الترخيص بوابة دخول منفصلة (تمنع تشغيل الواجهة أصلاً
بدون تفعيل صالح) بدون أي علاقة بقابلية فك تشفير البيانات نفسها.

## الآلية الفعلية المُنفَّذة (Phase 7) - أوفلاين بالكامل
1. عند أول تشغيل، تعرض شاشة التفعيل (features/licensing) معرف الجهاز
   المُولَّد (core/licensing/hardware_id_generator.dart) مع زر نسخ.
2. صاحب الصيدلية يُرسل هذا المعرف لك.
3. تستخدم `tools/license_generator.dart` (أداة منفصلة تمامًا عن التطبيق
   المُوزَّع - راجع docs/LICENSE_GENERATOR_GUIDE.md) لتوليد مفتاح موقّع
   بـ HMAC-SHA256 يخص هذا الجهاز فقط، مع تاريخ انتهاء اختياري.
4. صاحب الصيدلية يُدخل المفتاح مرة واحدة عبر شاشة التفعيل.
5. يُحفظ في جدول licenses محليًا، **ويُعاد التحقق من التوقيع ومطابقة معرف
   الجهاز في كل تشغيل لاحق للتطبيق** (وليس فقط عند أول تفعيل) - هذا يمنع نسخ
   ملف قاعدة البيانات نفسه (وبداخله سجل الترخيص) إلى جهاز آخر واستخدامه هناك.

## توليد معرف الجهاز (Hardware ID)
يُجرَّب بالترتيب: `wmic csproduct get uuid` ← PowerShell
`Get-CimInstance Win32_ComputerSystemProduct` ← قراءة MachineGuid من سجل
النظام ← احتياط أخير باسم الجهاز. لم يُختبر بعد على جهاز Windows فعلي من هذه
المحادثة - إذا فشلت الطرق الثلاث الأولى على جهازك، أخبرني بالخطأ بالضبط.

## توقيع مفتاح الترخيص: HMAC-SHA256 (رمزي/متماثل) وليس RSA
اخترت HMAC-SHA256 (عبر حزمة crypto الموجودة أصلاً في المشروع منذ Phase 1)
بدلاً من توقيع لامتماثل (RSA/ECDSA) لتفادي إضافة حزمة تشفير جديدة معقدة
(مثل pointycastle) لم أتمكن من اختبارها فعليًا في هذه البيئة. الفارق العملي:
مع HMAC، المفتاح السري نفسه المطلوب للتحقق موجود داخل التطبيق المُوزَّع، لذا
نظريًا مستخدم تقني متمرّس جدًا يقوم بهندسة عكسية كاملة للملف التنفيذي يمكنه
استخراجه وتوليد تراخيص مزوّرة بنفسه. هذا مقبول لهدف المشروع المعلن (منع
النسخ العرضي بين الصيدليات) وليس حماية من قرصنة احترافية مقصودة.

## نموذج تسعير مقترح (قرار تجاري تحدده أنت لاحقًا)
- ترخيص دائم لكل صيدلية (بدون تاريخ انتهاء - `dart run ... "الاسم"` بدون معامل الأيام)، أو
- ترخيص سنوي متجدد (`dart run ... "الاسم" 365`) - يُرفض تلقائيًا بعد الانتهاء
  برسالة واضحة في شاشة التفعيل، مع الحاجة لمفتاح جديد للتجديد.

## ملاحظة مهمة
هذا النظام يحمي من النسخ العرضي، لكنه ليس حماية عسكرية غير قابلة للكسر إطلاقًا -
لا يوجد نظام أوفلاين 100% محصّن ضد كل أنواع القرصنة. الهدف هو رفع الجهد المطلوب للكسر
إلى درجة غير مجدية اقتصاديًا لمعظم الحالات.
